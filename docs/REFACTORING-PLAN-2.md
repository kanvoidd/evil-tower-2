# План доработки архитектуры Evil Tower 2 (второй круг)

Первый круг (17 этапов) разложил код по слоям `domain / application / presentation /
infrastructure / composition`, сделал сцены координаторами и завёл проверки
(`npm run archtest`, расширенный `npm run selftest`). Второй круг доводит проект до чистой
архитектуры с правилами DDD:

- домен делится не по техническому признаку (`data/`, `logic/`, `engine/`), а **по доменным
  областям** (бой, забег, прогресс героя, экономика, награды, профиль);
- **правило отделено от расчёта**: сущность знает, *что* решает, а *как считать* — отдельная
  абстракция с реализацией (формула, политика, модификатор);
- файлы читаются: форматирование, размер, числа баланса с именами.

Документ — план, а не решение: каждое сделанное изменение по-прежнему записывается
отдельной записью в `PROJECT-DECISIONS.md`.

## 1. Оценка предложений

### 1.1 Линтер и правила форматирования — **согласен, делать первым**

Сейчас в проекте нет ни форматтера, ни линтера (`.eslintrc`, `.prettierrc`, `.editorconfig`
отсутствуют), и видны последствия:
- строки до 170+ символов, однострочные вызовы с десятком аргументов;
- **смешанные окончания строк**: часть файлов в CRLF, часть в LF (git при каждом `add`
  предупреждает «LF will be replaced by CRLF»);
- порядок импортов в каждом файле свой.

Уточнение: форматтер исправит **вид** кода, но не «кашу» в устройстве — длинный `switch` на 51
ветку останется длинным, только аккуратно перенесённым. Поэтому два инструмента:
- **Prettier** — только внешний вид;
- **ESLint** (`typescript-eslint`) — правила качества: размер файла и функции, сложность,
  `import type`, порядок импортов. Сначала как предупреждения — это карта «каши» для этапов C–F.

### 1.2 Разделить сложные сущности — **согласен, но главная цель не `GameController`**

`GameController` (296 строк) смешивает команды, ход, обучение, конец комнаты, гибель и итог
забега — его стоит разнести. Но самые тяжёлые файлы другие:

| Файл | Строк | Что внутри |
|---|---|---|
| `domain/logic/run/Run.ts` | 1836 | весь бой: урон, статусы, враги, добыча, конец хода, откат; `applyAbility` — один `switch` на **51 способность, ~410 строк** |
| `presentation/textures/Textures.ts` | 765 | все процедурные текстуры |
| `presentation/textures/PixelArt.ts` | 549 | пиксельные рисунки |
| `domain/logic/profile/Profile.ts` | 502 | кошельки, лавка, награды, достижения, автоматизация, настройки |
| `presentation/animations/effects/vfx/Vfx.ts` | 492 | 27 семейств эффектов |
| `domain/logic/skillTree.ts` | 366 | правила дерева **и** геометрия узлов (x/y — это раскладка экрана) |
| `presentation/animations/GameEventPlayer.ts` | 302 | 25 обработчиков событий боя в одном классе |
| `application/game/GameController.ts` | 296 | поток боя целиком |
| `tools/selftest.ts` | 1530 | все проверки одним файлом |

«Сохранять голову» решается одним приёмом: **фасад остаётся, внутренности делятся**. `Run`
по-прежнему реализует `IRunSession`, `Profile` сохраняет свои методы, `GameController` —
`execute()`. Снаружи (сцены, сим, selftest) ничего не меняется.

### 1.3 Баланс в `domain/balance`, разбор `types.ts` и `gameplay.ts` — **согласен с целью, но не с одной папкой на всё**

Чисел правил в логике много (грубый подсчёт литералов, кроме 0 и 1: `Run.ts` — ~138,
`stats.ts` — ~60, `FloorFactory.ts` — ~69), и часть — настройки баланса, спрятанные в коде
способностей (`0.6` сплеша, `0.05` от здоровья босса, «3 хода» яда). Их нельзя найти, не читая
бой целиком, и они расходятся с текстами: «250%» урона молнии написано в описании в
`MageFactory`, а `2.5` — отдельно в `Run.ts`.

Если собрать **все** числа в одну папку, получится тот же большой словарь в другом месте.
Правило:
- **число сущности живёт в её определении** — параметры способности в её `PerkDef` (фабрика
  героя), кривые врагов в фабрике этажа (уже так), цены вещей в реестрах оружия и брони;
- **число общего правила** — в балансе **своей доменной области** (см. 1.5), маленькими
  модулями по темам, каждое поле с описанием и единицей измерения.

`types.ts` (113 строк) — «ничей» файл: id героев, статусы карт, формат сохранения и язык
вперемешку. Типы уходят к владельцам (в доменные области и общее ядро), а на месте файла
остаётся папка-вход `types/index.ts` с реэкспортом — **импорт `'../types'` разрешается в папку
так же, как в файл**, поэтому импорты в проекте менять не придётся.

### 1.4 Отделить абстракцию от реализации (математика, расчёты) — **согласен, это главная ценность круга**

Сейчас правило и расчёт слиты в одном месте. Конкретные места:

| Где | Что слито | Во что превратить |
|---|---|---|
| `Run.currentDamage / contextDamage / afterArmor` | цепочка `if (талант) mul += …` с округлениями внутри боя | **модификаторы урона**: интерфейс `IDamageModifier`, по реализации на талант/пассивку («Ярость», «Резня», «Добивание»…), конвейер применяет их по порядку |
| `Run.defenseNow / reduce` | то же для защиты и входящего урона | **модификаторы защиты** и **снижения урона** — тот же приём |
| `Run.rollCrit` | пять правил крита подряд в одном методе | **политика крита** — упорядоченный список правил («крит комнаты», «Метка охотника», «каждый третий», шанс) |
| `stats.ts` (`buildPlayerStats`, ~70 полей) | сборка характеристик = сложение и проценты вручную | плоские поля постепенно заменяются **списками модификаторов**, которые прогресс героя выдаёт бою |
| `data/economy/soulPrices.ts` | цены талантов, способностей, классов — таблица + формула в функциях | **ценообразование**: интерфейс `ISoulPricing`, реализация по таблице ступеней |
| `FloorFactory.growth()` и кривые `FLOOR_*` | масштабирование врагов по этажу внутри фабрики контента | **масштабирование этажа**: интерфейс `IEnemyScaling`, фабрика этажа описывает только врагов |
| `Profile.repairCost`, `buyItem` | цена починки считается в профиле | **ценообразование лавки**: `IRepairPricing` в экономике |
| `TowerRun.clearRoom / end` (application!) | оплата комнаты (сумка + бонус), «без урона», рекорд — правила забега в слое приложения | **правила забега** в домене (`RoomPayout`, `RecordPolicy`); `TowerRun` в application только связывает их с сохранением и платформой |
| `Profile.dailyStatus / dayKey / dayDiff` | `new Date(...)` внутри домена — **скрытая зависимость от часового пояса устройства** | **календарь**: значение `DayKey` и порт/служба календаря; день игрока вычисляется явно |
| `rng.ts` (`randomSeed` через `Math.random`) | источник энтропии в домене | порт источника зерна; `Math.random` — только в инфраструктуре/корне композиции |
| `PlayerStats`: `crit` в процентах (18), `pierce` в долях (0.2) | единицы смешаны, отсюда `/ 100` в десятке мест | **типы значений** (см. ниже) |

Это одновременно решает и 1.3: у числа появляется хозяин — реализация абстракции.

**Главное ограничение:** при замене формул на модификаторы **порядок операций и округлений**
обязан остаться тем же (`Math.round` после каждого множителя, а не в конце), иначе сим
разъедется на копейки. Проверка — сим и selftest побайтно.

### 1.5 Доменные области по DDD — **согласен, с оговоркой про масштаб**

DDD здесь полезен двумя вещами: **единым языком** (слово в игре = имя в коде) и **границами
областей** (кто чем владеет и кто от кого зависит). Тяжёлую машинерию (репозитории на каждый
агрегат, шины событий, CQRS) для клиентской игры без сервера заводить не стоит — это та же
«структура ради структуры», от которой предостерегает первый круг.

Предлагаемые области (bounded contexts):

| Область | Что внутри (сейчас где) | Язык |
|---|---|---|
| **Бой** `combat/` | `Run`, поле и колода (`engine/`), карты и события (`game-data/`), статусы, способности, урон | комната, ход, удар, статус, способность |
| **Забег** `expedition/` | правила из `TowerRun`: вход в комнату, оплата, перенос героя, рекорд | забег, комната башни, сумка, рекорд |
| **Прогресс героя** `progression/` | `Hero`, `HeroClassState`, стратегии атаки, дерево талантов, характеристики, автопрокачка, сводка класса | герой, класс, метаморфоза, талант, ярус |
| **Экономика** `economy/` | кошельки, лавка, починка, расходники, цены душ | золото, души, кошелёк, вещь, прочность |
| **Награды** `rewards/` | награда дня, «Дар башни», достижения | награда, серия, достижение |
| **Профиль** `account/` | документ сохранения, миграции, настройки игрока, обучение | профиль, сохранение, версия |
| **Каталог** `catalog/` | фабрики и реестры контента (`data/`) | линейка, этаж, враг, способность |
| **Общее ядро** `shared/` | id (`LineageId`, `ClassId`…), `Rng`, `Signal`, типы значений | — |

Карта зависимостей (стрелка — «зависит от», циклов нет):

```
expedition ──► combat ──► catalog ──► shared
     │            ▲          ▲
     ├──► progression ───────┤
     ├──► economy ───────────┤
account ──► progression, economy, rewards ──► shared
rewards ──► economy
```

Правило области: снаружи её видно **только через `index.ts`** (публичный API области);
глубокие импорты во внутренности чужой области запрещены. Это проверяет `archtest`.

`Profile` при этом становится **корнем агрегата «аккаунт игрока»**, который держит части из
своих областей (кошельки — экономика, герои — прогресс, календарь наград — награды) и сохраняет
их одним документом — так и сохранение остаётся одним файлом, и области не знают друг о друге.

**Единый язык — одно неудобное место:** `Run` — это бой в **одной комнате**, а «забег» в игре —
цепочка комнат (из-за этого есть отдельная запись в GOTCHAS). **Решено:** переименовать
`Run` → `RoomBattle` и связанные имена механическим шагом на этапе B (см. B3 и раздел 6).

## 2. Мои дополнения

1. **Окончания строк и `.gitattributes`** — нормализовать все файлы в LF до форматирования,
   иначе каждый следующий дифф будет шуметь.
2. **Параметры способностей — в `PerkDef`, числа в описаниях — через `{n}`.** STYLE.md уже
   требует «не хардкодить числа в тексте», параметры в данных сделают это возможным.
3. **Способности — реестр обработчиков вместо `switch`**: по классу на способность с общим
   интерфейсом (тот же приём, что у стратегий атаки линеек).
4. **Типы значений без затрат в рантайме** (branded types): `Percent` (0–100), `Ratio` (0–1),
   `Gold`, `Souls`, `Turns`, `CellIndex`. В скомпилированном коде это те же числа — сим не
   меняется, — а перепутать проценты с долями или золото с душами станет ошибкой компиляции.
5. **Формат сохранения и миграции — в домен** (`account/save/`): перенос старых форматов сейчас
   живёт в `ProfileStore.merge` и ничем не проверяется.
6. **Геометрия дерева навыков — в presentation**: x/y узлов не нужны правилам покупки.
7. **`selftest` — по файлам на тему**, один вход, вывод прежний; сюда же — тесты каждой
   реализации абстракции отдельно (модификатор, политика, ценообразование) на маленьких числах.
8. **Headless-прогон интерфейса** (26 сценариев) — в `tools/`.
9. **BUG-002 и BUG-003** — отдельно, после рефакторинга: оба меняют поведение.

## 3. Правила на весь второй круг

- **Фасады не меняются.** Публичные контракты (`IRunSession`, `IRunState`, методы `Profile`,
  `execute()` контроллеров, `SceneServices`) остаются. Меняется то, что за ними.
- **Бой побайтно тот же.** После каждого шага `npm run selftest` и `npm run sim` по четырём
  линейкам дают тот же вывод, что до шага. Особенно важно сохранить **порядок вызовов
  генератора случайных чисел** и **порядок округлений** в формулах.
- **Абстракция там, где есть выбор или правило.** Интерфейс заводится, если у него есть
  (или обоснованно будет) больше одной реализации, или если он отделяет правило от способа
  расчёта. Интерфейс ради интерфейса — нет.
- **Один шаг — один коммит — одна запись в `PROJECT-DECISIONS.md`.** Механические шаги
  (форматирование, переезд папок) — отдельными коммитами без правок логики; их хеши —
  в `.git-blame-ignore-revs`.
- **Проверки после каждого шага:** `npm run typecheck`, `npm run lint` (после этапа A),
  `npm run archtest`, `npm run selftest`, `npm run sim`, headless-прогон интерфейса.

## 4. План по этапам

Порядок выбран так, чтобы механические диффы шли отдельно от содержательных и чтобы новые
файлы сразу создавались в своих доменных областях, а не переезжали дважды.

### Этап A. Правила кода и форматирование

A1. `.gitattributes` (`* text=auto eol=lf`) и `.editorconfig`; перенормализация репозитория
    отдельным коммитом.

A2. Prettier: **`printWidth: 100`** (решено), одинарные кавычки, запятые в конце, точки с запятой.
    Скрипты `format` и `format:check`. Код сейчас местами шире 170 символов, поэтому при 100
    переносов будет много — это ожидаемо и делается одним коммитом (A4).

A3. ESLint (flat config, `typescript-eslint`). **Решено:** самое вредное для кода — ошибки,
    остальное — предупреждения.

| Уровень | Правила |
|---|---|
| **Ошибка** — форматирование | расхождение с Prettier (`format:check` в том же прогоне, что и lint) |
| **Ошибка** — импорты | `consistent-type-imports` (типы — только `import type`), порядок импортов (пакеты → слои снаружи внутрь → соседние файлы), `no-duplicate-imports`, неиспользуемые импорты |
| **Ошибка** — сложность функции | `complexity` ≤ 15, `max-depth` ≤ 4 (вложенность `if`/циклов), `max-nested-callbacks` ≤ 3 |
| Предупреждение | `max-lines` (≈300 на файл), `max-lines-per-function` (≈60), `max-params` (4, дальше — объект-параметр), `no-explicit-any` (в SDK платформы — точечно разрешён), `no-magic-numbers` (включается после этапа D) |

    Правила слоёв не дублировать — это `archtest`.

    **Переходный период.** Сложность как ошибка сразу «упадёт» на существующем коде
    (`applyAbility` в `Run`, `buildPlayerStats` и др.). Такие места заносятся в явный список
    исключений в конфиге ESLint с пометкой этапа, который их уберёт; новый код исключений
    не получает. Список сокращается по мере этапов D–G и к концу круга пуст.

A4. Один коммит `style:` — Prettier по всему проекту, без правок логики.

A5. Отчёт ESLint — список целей для этапов D–G.

**Готово, когда:** `lint` и `format:check` проходят (ошибок нет, исключения перечислены явно),
окончания строк одинаковые, есть запись в `PROJECT-DECISIONS.md` о правилах кода.

### Этап B. Доменные области: карта и переезд (механический)

B1. Документ `docs/DOMAIN.md`: области, их язык (глоссарий «слово игры → имя в коде»), карта
    зависимостей, публичный API каждой области. Запись в `PROJECT-DECISIONS.md`.

B2. Переезд папок домена по областям одним механическим шагом (скрипт переписывает импорты,
    как на этапе 0 первого круга): `engine/` + `game-data/` + `logic/run/` → `combat/`;
    `logic/hero`, `skillTree`, `stats`, `autoSkill`, `traits` → `progression/`; `data/` →
    `catalog/`; `logic/profile` → `account/`; `rng`, `signal` → `shared/`. У каждой области —
    `index.ts`. Логика не меняется ни в одной строке.

B3. **Переименование боя в комнате** (решено) — механическим шагом, отдельным коммитом, средствами
    переименования TypeScript, без правок логики:

| Было | Стало |
|---|---|
| `Run` | `RoomBattle` |
| `RunFactory` | `RoomBattleFactory` |
| `IRunSession`, `IRunState` | `IBattleSession`, `IBattleState` |
| `RunInit`, `RunDeps`, `RunSnapshot`, `RunTotals`, `RunCarryStats` | `BattleInit`, `BattleDeps`, `BattleSnapshot`, `BattleTotals`, `BattleCarryStats` |
| папка `logic/run/` | `combat/room-battle/` |

    Имена **забега** не трогаются — там «run» стоит по смыслу: `TowerRun`, `RunCarry`,
    `RunSummary`, `RunEndReason`. Запись «Run и забег — разные вещи» в GOTCHAS заменяется
    записью о новом имени; переменные `run` в сим, selftest и сценах, которые держат бой
    комнаты, переименовываются в `battle` в том же шаге.

B4. `archtest`: правила областей — импорт чужой области только через её `index.ts`, карта
    зависимостей из B1, отсутствие циклов между областями; `shared/` не зависит ни от чего.

**Готово, когда:** домен разложен по областям, бой в комнате называется `RoomBattle`,
`archtest` проверяет границы областей, сим и selftest побайтно те же.

### Этап C. Типы, типы значений, баланс, параметры сущностей

C1. `domain/types.ts` → `domain/types/index.ts` (реэкспорт); типы — владельцам: id — в
    `shared/`, `SaveData` и соседи — в `account/save/`, `CardKind`/`StatusKind` — в `combat/`,
    `ConsumableId`/`ItemSlot` — в `economy/` или `catalog/`, `TalentPath` — в `progression/`.

C2. Типы значений (branded): `Percent`, `Ratio`, `Gold`, `Souls`, `Turns`, `CellIndex` в
    `shared/`; перевод процентов в доли — одной функцией вместо `/ 100` в десятке мест.

C3. Баланс по областям вместо `gameplay.ts`: `combat/balance/CombatBalance` (крит, предел
    снижения урона бронёй, ослабление, воскрешение), `combat/balance/ConsumableBalance`,
    `combat/balance/LootBalance`, `progression/balance/ProgressionBalance` (цена нового героя,
    возврат при отмене метаморфозы). Каждое поле — с описанием и единицей.

C4. Параметры способностей: `PerkDef.params` (типизированные по способности), числа из
    `Run.applyAbility` переезжают в фабрики героев.

C5. **Тексты — отдельно от логики** (решено). Названия и описания способностей, талантов, классов
    и прочего контента уходят из фабрик героев и этажей (`{ ru, en }` рядом с кодом) в словари
    `src/i18n/ru.ts` и `src/i18n/en.ts` — как и требует STYLE.md («источник истины — ru.ts»):
- ключи по id сущности: `perk.<id>.name`, `perk.<id>.desc`, `talent.<id>.name` и т. д.;
- числа в описаниях — только плейсхолдерами из `params` (`{dmg}`, `{turns}`), «голых» чисел
  в текстах нет;
- фабрики описывают сущность (id, слот, цена, цель, `params`), но не хранят текст;
- selftest проверяет: у каждой сущности есть оба перевода, каждый плейсхолдер текста есть
  в `params`, в текстах способностей нет чисел.

    Тексты при переносе не меняются (только числа заменяются плейсхолдерами, дающими ту же
    строку). Правка формулировок по STYLE.md — отдельной задачей, не в этом круге.

C6. Геометрия дерева навыков (x/y узлов, отступы веток) — из `skillTree` в
    `presentation/views/skill-tree/`: правилам покупки координаты не нужны, это раскладка экрана.

**Готово, когда:** `types.ts` и `gameplay.ts` — только реэкспорты или удалены, у каждого числа
баланса есть имя и хозяин, в фабриках нет текстов, сим побайтно тот же.

### Этап D. Бой: правила отдельно от расчёта, `Run` — фасад

Самый большой и рискованный этап. Сначала абстракции расчёта, потом разбор класса.

D1. **Конвейер урона героя**: `IDamageModifier` (`apply(dmg, ctx): number`) и реализации по
    талантам/пассивкам; `DamagePipeline` применяет их в прежнем порядке с прежними округлениями.
    То же для **защиты** (`IDefenseModifier`) и **снижения входящего урона** (`IDamageReduction`).

D2. **Политика крита**: упорядоченный список правил, первое сработавшее решает; порядок
    вызовов `rng` — как сейчас.

D3. Модификаторы выдаёт **прогресс героя**: из талантов и пассивок строятся списки
    модификаторов, бой только применяет их. Плоские поля `PlayerStats` уходят по одному,
    по мере переноса формул.

D4. **Реестр способностей**: `IAbility` + класс на способность (или на группу с общим кодом),
    `AbilityContext` даёт только нужное (урон, статусы, поле, события, `rng`). Переносить
    пачками по линейкам.

D5. **Разбор `Run`** на части с общим состоянием комнаты (`RoomState`): `PlayerActions`,
    `StatusEffects`, `EnemyTurn` (ответ врагов, удар по герою, спасение от смерти), `Loot`,
    `RoomFlow` (ход, переход, конец комнаты), `Snapshot`. `Run` остаётся фасадом `IRunSession`.

D6. Включить `no-magic-numbers` для `domain` и `application` (разрешены 0, 1, −1, 2, 100)
    и разобрать остаток.

**Главный риск** — порядок случайностей и округлений: ни один вызов `rng` и ни один
`Math.round` не должен поменяться местами. Сим побайтно ловит любое отклонение.

**Готово, когда:** `Run.ts` ≤ ~300 строк, ни один файл боя не больше ~300 строк, `applyAbility`
нет, у каждого модификатора и правила крита — свой тест в selftest, сим побайтно тот же.

### Этап E. Забег, экономика и прогресс: формулы как доменные службы

E1. **Забег** (`expedition/`): `RoomPayout` (сумка + бонус комнаты, «без урона»),
    `RecordPolicy` (рекорд пишется сразу после комнаты), перенос героя между комнатами.
    `TowerRun` в application остаётся координатором: вызывает правила, пишет сохранение,
    шлёт рекорд платформе.

E2. **Ценообразование душ** (`progression/`): `ISoulPricing` — цена ранга таланта, способности,
    класса, метаморфозы, возврат при отмене; реализация по таблице ступеней.

E3. **Масштабирование этажей** (`catalog/` или `combat/`): `IEnemyScaling` (кривые `FLOOR_*`,
    доля награды забега); фабрики этажей описывают врагов и комнаты, но не формулу роста.

E4. **Экономика** (`economy/`): `IRepairPricing`, правила лавки «вещь слабее надетой»,
    предел запаса расходников — из `Profile` в службы области.

E5. **Источник случайности**: `randomSeed` (`Math.random`) — из домена в порт, реализация —
    в корне композиции.

**Готово, когда:** в `application/` нет правил игры (только порядок вызовов), у каждой формулы
есть интерфейс, реализация и тест; сим побайтно тот же.

### Этап F. Поток боя и показ событий

F1. `GameController` → фасад над частями: `TurnFlow` (ход, итог хода, автоприменение),
    `TutorialGuide`, `RoomOutcome` (победа, переход дальше), `DeathFlow` (гибель, воскрешение
    за видео, «Возвращение»), `RunEnd` (итог забега, удвоение). `execute()` и порты не меняются.

F2. `GameEventPlayer` → реестр обработчиков по типу события, обработчики группами (бой,
    движение, добыча, эффекты).

**Готово, когда:** ни один файл потока боя не больше ~150 строк; selftest проверяет поток
«гибель → воскрешение → гибель → итог» и «побег».

### Этап G. Аккаунт игрока, награды, сохранения

G1. `Profile` — корень агрегата «аккаунт»: части `HeroWallets` (экономика), герои (прогресс),
    `DailyRewards` и `AchievementTracker` (награды), `AutomationSettings`, `PlayerSettings`.
    Методы `Profile` сохраняются и делегируют частям.

G2. **Календарь наград**: значение `DayKey`, служба календаря (день игрока, разница дней)
    вместо `new Date` в `Profile`; день задаётся явно и проверяется в selftest при любом часовом
    поясе.

G3. **Сохранение** (`account/save/`): формат, `freshData`, версии и **миграции по шагам**
    (из `ProfileStore.merge`); `ProfileStore` — только чтение и запись. Тесты миграций в selftest.

### Этап H. Presentation: процедурная графика — отдельный блок, не разбираем

**Решено:** процедурные спрайты (`Textures.ts`, `PixelArt.ts`, `SvgIcons.ts`) и эффекты (`Vfx.ts`)
будут заменены картинками (jpg и др.), поэтому внутри их не делим и не улучшаем. Задача этапа —
только **изолировать** их как сменный блок:
- `presentation/textures/` остаётся самостоятельным блоком: остальной код знает только ключи
  текстур (`hero_<classId>`, `perk_<id>` …), а не то, как они нарисованы;
- загрузка готовых картинок (`queueExternalArt`: файл с именем ключа подменяет заглушку) —
  единственная точка замены; список ключей — в одном месте;
- в ESLint этот блок получает исключение по размеру файлов (правила импортов и форматирования
  действуют).

Геометрия дерева навыков (x/y узлов) — к этому этапу не относится: она переезжает из домена
в `presentation/views/skill-tree/` на этапе C (типы и расчёты, которые не нужны правилам).

### Этап I. Проверки и хвосты

I1. `tools/selftest.ts` → `tools/selftest/` по темам (бой, прогресс, экономика, забег, аккаунт,
    приложение), один вход, вывод прежний.

I2. Headless-прогон интерфейса → `tools/smoke.mjs` + `npm run smoke`.

I3. BUG-002 и BUG-003 — отдельными коммитами `fix:`; для BUG-002 — осознанно обновить эталон
    сима мага.

I4. README («Структура»), `docs/DESIGN.md`, `docs/DOMAIN.md`, `PROJECT-DECISIONS.md` — по итогам.

## 5. Что не делаем в этом круге

- Не меняем механику и баланс: цель — те же числа в понятных местах.
- Не заводим репозиторий на каждый агрегат, шину событий, CQRS и DI-контейнер: для клиентской
  игры без сервера хватает одного хранилища, доменных `Signal`, корня композиции и конструкторов.
- Не переписываем формулировки текстов по STYLE.md — только переносим их в словари.
- Не разбираем процедурную графику — она будет заменена картинками.
- Не заводим контроллеры экранам без решений (уровни, достижения).

## 6. Принятые решения (ответы на вопросы плана)

| # | Вопрос | Решение | Где в плане |
|---|---|---|---|
| 1 | Ширина строки для Prettier | **100 символов** | A2 |
| 2 | Тексты способностей и талантов: в фабриках или в словарях | **Отделить текст от логики**: тексты — в `i18n/ru.ts` и `i18n/en.ts` по id сущности, числа — плейсхолдерами из `params` | C5 |
| 3 | Процедурная графика (этап H) | Будет заменена картинками (jpg и др.) — **лежит отдельным блоком**, внутри не разбираем, только изолируем как сменную часть | H |
| 4 | Строгость ESLint | **Ошибки**: форматирование, импорты, сложность функции. **Предупреждения**: размер файлов и функций, число параметров, `any`, «магические» числа. Существующие нарушения — явным списком исключений до их этапа | A3 |

## 7. Порядок и объём

| Этап | Суть | Риск | Объём |
|---|---|---|---|
| A | правила кода, форматирование | низкий (механика) | небольшой, один большой дифф |

| D | бой: модификаторы, крит, способности, разбор `Run` | **высокий** (порядок случайностей и округлений) | самый большой |

| I | проверки, баги, документы | низкий | небольшой |

Порядок: **A → B → C → D → E → F → G → H → I**.
