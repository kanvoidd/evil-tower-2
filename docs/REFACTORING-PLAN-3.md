# План третьего круга: содержимое героев — классы, способности, перки, таланты

Второй круг разложил домен по областям и отделил правила от расчёта. Содержимое героев при
этом осталось в четырёх фабриках (`WarriorFactory`, `MageFactory`, …): линейка, классы,
способности и дерево талантов — одним файлом на линейку. Третий круг готовит проект к
следующему этапу — **геймдизайну**: добавить способность или перк, заменить стартовую
способность, перенести её в другой класс, переделать дерево талантов должно быть правкой
определений, а не архитектуры.

Основа — предложение «План рефакторинга хранения игрового контента» с поправками по коду
(раздел 1). Документ — план, а не решение: каждое сделанное изменение записывается отдельной
записью в `PROJECT-DECISIONS.md`.

**Статус (2026-09-25):** выполнены этапы C (классы), A (способности и перки), D (таланты) и
E (дерево прокачки); следующий — F (документация).

Круг затрагивает только классы, способности, перки, таланты и дерево прокачки как их
потребителя. Враги, вещи, экономика, формат сохранения, `PlayerStats` и устройство боя не
переделываются.

**Инвариант каждого шага:** `npm run selftest` и `npm run sim -- <линейка>` совпадают с
эталоном побайтно, снимок каталога (линейки, классы, способности, таланты, узлы и связи
деревьев) — тоже, пока шаг сознательно не меняет его вид; формат сохранения не меняется.

## 1. Поправки к предложению по коду

### 1.1 Id таланта сейчас — его место в дереве

Талант называется по позиции: `mage/a1-2` (класс, путь, ярус, место в цепочке). На этом id
держатся ключи сохранения (`LineageSave.ranks` — узлы `tal/mage/a1-2`) и 196 названий в
словарях (`talent.mage/a1-2.name`). Поэтому:
- **узел дерева сохраняет позиционный id** — это ключ сохранения, формат не меняется;
- **определение таланта получает свой id** по смыслу, и название переезжает на него: талант,
  перенесённый в дереве, уносит с собой и эффект, и название.

Ограничение, которое остаётся: сохранение помнит ранг **позиции**, а не таланта. Если
геймдизайн переставит таланты, у старых сохранений ранги останутся на прежних местах. Хранить
ранги по id таланта — изменение формата сохранения (шаг в `SAVE_MIGRATIONS`), в этот круг не
входит.

### 1.2 Готовых общих поведений у способностей нет

В бою 42 класса способностей, каждый привязан к одному id. Способности «по конфигурации»
(`behavior: 'damage'`) потребовали бы переписать бой. Реально и полезно другое: **отделить
поведение от id**. Определение способности называет поведение, которое её исполняет; сейчас
поведение совпадает с id, но новая способность с механикой существующей (другие числа, другой
класс, своё название) больше не требует кода — только определение.

### 1.3 Центральные списки становятся производными, а не исчезают

- `AbilityId` выводится из списка определений способностей. Сам список (импорт каждого файла)
  остаётся: `tsx` в selftest не умеет подхватывать файлы по маске. Добавить способность —
  файл определения и строка в списке линейки.
- Список поведений (`AbilityBehaviorId` с видом чисел каждого) остаётся центральным: за каждым
  поведением стоит код боя, и компилятор должен проверить, что числа определения подходят
  поведению.
- `ClassId` остаётся объединением: `ClassDef.parent` ссылается на него, и вывод id из
  определений дал бы циклический тип. Новый класс — редкое событие, которое и так требует
  дерева и баланса.
- `TalentFx` не исчезает, а превращается в типизированные виды эффектов: бою нужно знать, как
  применять каждый эффект, а `PlayerStats` в этом круге не переделывается. Выигрыш — смысловые
  имена чисел вместо `v/v2`, правило сложения в эффекте, а не в дереве, и дерево без знания
  эффектов.

### 1.4 Тексты, иконки и бой привязаны к перку, а не к способности

Названия и описания — `perk.<класс>_<слот>.*`, иконки — `perk_<класс>_<слот>`, бой держит
перезарядки и «раз за комнату» по id перка, а откат проверяет `perks.includes('magister_p3')`.
Способность, перенесённая в другой класс, потеряла бы текст, иконку и (для отката) работу.
После круга **тексты, иконки и бой адресуют способность по её id**, перк существует только в
каталоге и прогрессе.

### 1.5 `vfx` уходит в presentation

Стиль вспышки по умолчанию нужен бою только затем, чтобы вставить событие `fx`, если
способность ничего не нарисовала сама, и текстурам — для иконки. После круга событие несёт id
способности, а стиль выбирает таблица в presentation (`Record<AbilityId, VfxStyle>`, полноту
проверяет компилятор). Стили эффектов внутри кода способностей (`style: 'bolt'`) — словарь
событий боя, они остаются.

### 1.6 Файл на класс, а не на каждую способность и талант

Предложение раскладывает содержимое по файлу на сущность (`abilities/lightning.ts`,
`talents/warm-up.ts`): это около шестидесяти файлов способностей и двухсот файлов талантов по
5–10 строк. Решение разработчика — группировать по классу: `abilities/<класс>.ts` держит
способности, которые открывает этот класс, `talents/<класс>.ts` — таланты и дерево этого
класса. Файл читается целиком за раз, в нём видно всё, что класс даёт, и он же — единица
переделки («переделываем пироманта» — файлы пироманта). Классы остаются по файлу: они и есть
та единица, по которой сгруппировано остальное.

### 1.7 Прочее

- В примере предложения `ranks: [3, 6]` рядом с `statBonus('crit', [3, 6])` — одни данные
  дважды: число рангов выводится из значений эффекта.
- Этапы A и B предложения — один шаг: разрезать `PerkDef` на две сущности, не переключив всех
  потребителей, нельзя.
- Это пересмотр решения об абстрактной фабрике содержимого (записи «Класс героя — состояние…»,
  «Стиль атаки: каталог называет его по id…» и правило проекта): фабрики героев исчезают как
  способ записи содержимого.

## 2. Модель после круга

| Сущность | Что описывает | Где |
|---|---|---|
| Линейка `LineageDef` | ресурс, база, стиль атаки, цена спасения от смерти | `catalog/heroes/<линейка>/lineage.ts` |
| Класс `ClassDef` | линейка, ступень, родитель, бонусы, **перки по слотам** | `catalog/heroes/<линейка>/classes/<класс>.ts` |
| Способность `AbilityDef` | что делает: механика (`behavior`), числа (`params`), цена, цель, перезарядка, «раз за комнату», вид (кнопка / пассивка / базовое действие) | `catalog/heroes/<линейка>/abilities/<класс>.ts` — способности, которые открывает класс |
| Перк `PerkDef` | выдача способности классу на слоте (`start`, `p2`, `p3`, `legend`) | выводится из `ClassDef.perks` реестром |
| Талант `TalentDef` | постоянный эффект по рангам (`TalentEffect` с именованными числами) | `catalog/heroes/<линейка>/talents/<класс>.ts` — вместе с деревом класса |
| Дерево класса `TalentTree` | ярусы и цепочки путей из талантов | там же, `talents/<класс>.ts` |
| Узел дерева `TreeNode` | позиция, связи, позиционный id (ключ сохранения) | строит `progression/skill-tree` |
| Поведение способности `IAbility` | как способность работает в бою | `combat/abilities/<линейка>/<поведение>/` |

Реестры (`LINEAGES`, `CLASSES`, `CLASS_DEFINITIONS`, `ABILITIES`, `PERKS`, `TALENTS`) —
производные индексы над списками линеек (`HEROES`), а не место, куда дописывают содержимое.

### Как будет выглядеть работа геймдизайнера

| Задача | Что правится |
|---|---|
| Изменить числа способности | её запись в `abilities/<класс>.ts` |
| Заменить стартовую способность класса | строка `perks.start` в файле класса |
| Перенести способность в другой класс | строка `perks` в двух файлах классов |
| Новая способность на готовой механике | запись в `abilities/<класс>.ts`, строка в `perks` класса, тексты в двух словарях, стиль вспышки в `ABILITY_FX` |
| Новая механика | то же + id и вид чисел в `AbilityBehaviorParams`, класс в `combat/abilities/`, строка в `ABILITY_BEHAVIORS` (у пассивки — правило в частях боя) |
| Изменить бонусы класса | файл класса |
| Новый талант на готовом эффекте | запись в `talents/<класс>.ts` на нужном месте дерева, название в двух словарях |
| Переставить таланты | файл дерева класса (сохранения помнят позицию — см. 1.1) |

## 3. Этапы

### Этап C — классы и линейки (первым: ни от чего не зависит) — выполнен

1. Линейка — `catalog/heroes/<линейка>/lineage.ts`, классы — по файлу в `classes/`.
2. `ClassDef.mods` → `bonuses` (что это — видно из имени).
3. Список линеек `HEROES` (`HeroContent`: линейка и её классы; на этапах A–D — способности и
   деревья) — порядок линеек в игре. `LINEAGES`, `CLASSES`, `CLASS_ORDER` выводятся из него.
4. Шаблонный метод `HeroFactory.createClassDefinitions()` переезжает в реестр классов.
5. `createLineage()` и `createClasses()` уходят из фабрик; фабрики пока выпускают только
   перки и таланты.
6. Проверки: снимок каталога совпадает; метаморфозы и `HeroClassState` — selftest.

### Этап A — способности и перки — выполнен

1. `AbilityDef` — определение способности (поведение, `params`, цена, цель, перезарядка,
   «раз за комнату», вид). `defineAbility()` выводит механику и проверяет вид чисел.
   Способности — `abilities/<класс>.ts` линейки; смысл чисел описан у механики
   (`AbilityBehaviorParams`).
2. Механика отделена от id: вид чисел — по механике (`AbilityBehaviorParams`, бывший
   `AbilityParams`); `AbilityId` — строка из определения, общего списка id нет.
3. Перки — `ClassDef.perks` (слот → способность); `PerkDef` (id, класс, слот, способность)
   выводит реестр. Цена, цель, перезарядка на перке не дублируются.
4. Бой адресует способность по id: `PlayerStats` держит определения способностей, перезарядки
   и «раз за комнату» — по id способности, пассивки и их числа — по поведению из способностей
   героя (а не из глобального `PERK_BY_ABILITY`), откат проверяет способность, а не
   `magister_p3`. Команда и события HUD — тоже по способности.
5. Тексты — `ability.<id>.name/desc`, иконки — `ability_<id>` (файлов иконок в
   `src/assets/images` пока нет — переименование ничего не ломает).
6. `vfx` — таблица в presentation; событие вспышки по умолчанию несёт id способности.
7. `createPerks()` уходит из фабрик.
8. Проверки: у каждого поведения, у которого есть кнопка, есть реализация; числа способности
   подходят её поведению (компилятор); у каждой способности не больше одного перка; снимок
   каталога и selftest/sim совпадают.

### Этап D — таланты — выполнен

Таланты класса и его дерево — один файл `talents/<класс>.ts` (раздел 1.6).

1. `TalentDef` — id по смыслу и эффект `TalentEffect`: виды эффектов с именованными числами
   (характеристика, изменение способностей, особое правило; пара «шанс / сила» — полями
   `chance` и `power`). Число рангов — из значений эффекта.
2. `TalentTree` класса — ярусы с цепочками по путям, ссылками на определения.
   Позиционные id узлов (`mage/a1-2`) выводятся из дерева, как и сейчас.
3. Названия — `talent.<id таланта>.name`.
4. Правило сложения (сумма, максимум для силы пары) — в эффекте; `talentValue2` и `v/v2`
   удаляются. Значок синергии в дереве — из вида эффекта, а не из отдельного списка.
5. `createTalents()` и `HeroFactory` удаляются.
6. Проверки: снимок узлов и связей деревьев совпадает, суммы эффектов на эталонных
   прокачках — тоже; selftest/sim совпадают.

### Этап E — дерево прокачки — выполнен

1. Сумма эффектов талантов (`talentBonuses`) уходит из дерева в характеристики героя:
   дерево отвечает, какие узлы изучены, а что они дают — эффект таланта.
2. `skillTree.ts` не импортирует `TalentFx` и значения талантов — только структуру,
   состояние узлов, цены, покупку и отказ от класса.
3. Проверки: покупка, отказ от финального класса, метаморфоза, автопрокачка — selftest и
   `npm run smoke`.

### Этап F — документация

`docs/DOMAIN.md` (карта каталога, глоссарий: способность / перк / талант / узел),
`STYLE.md` (ключи текстов), README, запись итога в `PROJECT-DECISIONS.md`, правило проекта о
содержимом в памяти разработки.

## 4. Критерии готовности

- **Классы:** новый класс — его файл, строка в списке линейки и id в `ClassId`.
- **Способности:** способность на готовой механике не требует правок в бою, реестрах и
  объединениях; `PerkDef` не хранит механики.
- **Перки:** перенос способности между классами — правка `perks` двух классов, тексты и иконка
  идут со способностью.
- **Таланты:** талант на готовом эффекте — запись в дереве своего класса; числа названы по смыслу.
- **Дерево:** `skillTree.ts` не знает эффектов талантов и механик способностей.
- **Фабрики:** `HeroFactory` и конкретные фабрики героев удалены.
- **Реестры:** только поиск и производные индексы.
