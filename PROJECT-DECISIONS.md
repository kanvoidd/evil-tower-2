## [2026-09-24] Карта сцен: разная глубина архитектуры для разных типов экранов
**Решение:** сцены делятся на пять типов, и глубина разделения на слои зависит от типа, а не одинакова для всех:

| Тип | Сцены | Что получает |
|---|---|---|
| Bootstrap | BootScene | только запуск: собрать зависимости и загрузить ресурсы (composition root), без контроллера |
| Main Navigation | HubScene | контроллер + вид: навигация, награды дня, автопрокачка |
| Selection / Progression | ClassSelectScene, SkillTreeScene, LevelsScene | дерево и выбор класса — контроллер и сценарии (метаморфоза); уровни — только вид |
| Meta Gameplay | ShopScene, AchievementsScene, SettingsScene | лавка — сценарии покупки; достижения — вид; настройки — лёгкий контроллер |
| Core Gameplay | GameScene | полный поток: команды → контроллер → бой → события → анимации/HUD |

**Контекст:** план рефакторинга (два цикла: эталон на GameScene, затем миграция остальных сцен). Для экрана достижений полный набор «контроллер + сценарии + порты» был бы церемонией без пользы.
**Альтернативы:** один шаблон «сцена → контроллер → сценарии → вид» для всех экранов — отвергнут: лишние слои там, где нет бизнес-логики.
**Последствия:** новая сцена сначала относится к типу из таблицы; контроллер заводится, только если в сцене есть решения (что можно, что изменить, куда сохранить, куда перейти). Перенос функции из файла в файл ради «контроллера» не делается.

## [2026-09-24] Слои проекта и их папки
**Решение:** код разложен по слоям, у каждого слоя своя папка в `src/`:

- `src/domain/` — правила игры и контент: `data/` (контент из фабрик героев и этажей), `engine/` (поле 3×3, колода, журнал событий), `game-data/` (карта, события боя), `logic/` (бой в комнате `Run`, дерево талантов, характеристики, автоматизация), `types.ts` (общие типы и формат сохранения), `gameplay.ts` (числа правил).
- `src/application/` — сценарии и контроллеры: что делать в ответ на действие игрока; с внешним миром говорит через интерфейсы (порты).
- `src/presentation/` — всё, что рисует и слушает ввод (Phaser): сцены, виды, HUD, анимации, компоненты интерфейса, текстуры, тема.
- `src/infrastructure/` — внешняя граница: сохранения (`Store`), звук, реклама, SDK Яндекс Игр.
- `src/composition/` — composition root: собирает конкретные реализации и отдаёт их сценам (появляется на этапе BootScene).
- `src/i18n/` — тексты; ресурс слоя presentation, лежит в корне `src`, потому что на `src/i18n/ru.ts` как на источник истины ссылается `STYLE.md`.

Внутренняя структура доменных папок (`data/heroes/mage-factory/...`, `logic/run/...`) при переносе не менялась — папки просто стали вложенными в `domain/`.
**Контекст:** до рефакторинга слои угадывались только по именам (`data`, `logic`, `ui`, `systems`, `sdk`, `scenes` рядом в корне), а `config.ts` смешивал числа правил, цвета, шрифты и рекламу. Для правил зависимостей и их автоматической проверки слой должен читаться по пути файла.
**Альтернативы:** оставить доменные папки в корне `src` и считать доменом «всё остальное» — отвергнуто: границу слоя не видно в дереве проекта, и новая папка в корне попадала бы в домен по умолчанию.
**Последствия:** новый файл кладётся в папку своего слоя. Путь файла = его слой; на этом держится проверка зависимостей.

**Решение:** `src/config.ts` удалён. Числа правил (`GAMEPLAY`) — `domain/gameplay.ts`; размеры экрана, шрифты, палитра, тайминги и карусель — `presentation/theme/`; политика полноэкранной рекламы — `application/ads/adPolicy.ts` (`AD_POLICY`); кулдаун «Дара башни» — `domain/data/economy/giftCooldown.ts` (`GIFT_COOLDOWN_MS`) рядом с наградой дара. **Последствия:** домен не импортирует ничего из `presentation/theme`. Новая константа кладётся к тому слою, который её читает.

## [2026-09-24] Правила зависимостей между слоями
**Решение:** зависимости идут только внутрь — `presentation → application → domain`, а `infrastructure` и `composition` стоят снаружи и подключаются через интерфейсы:

| Слой | Может импортировать | Не может импортировать |
|---|---|---|
| domain | только domain | Phaser, DOM-API, application, presentation, infrastructure, composition, i18n |
| application | domain, application | Phaser, presentation (конкретные сцены и виды), infrastructure, composition |
| presentation | domain, application, i18n, Phaser | infrastructure, composition |
| infrastructure | domain, application (порты), сторонние SDK | presentation, composition |
| composition | всё | — (единственное место, где встречаются все слои) |

Внутри домена `engine` не знает правил (`logic`), а `logic/run` получает зависимости готовыми от `RunFactory`.
**Контекст:** до рефакторинга сцены и компоненты интерфейса напрямую импортировали `Store`, `AUDIO`, `YSDK`, а `Store` держал правила лавки, наград и прокачки. Любая правка правил требовала править сцены, а логику нельзя было проверить без Phaser.
**Последствия:** сцена или вид не вызывают `Store`/`AUDIO`/`YSDK` напрямую — только через контроллер, сценарий или интерфейс, реализацию которого отдаёт composition root. Домен и application проверяются без Phaser и без браузера (`npm run selftest`).

## [2026-09-24] События боя проигрывает GameEventPlayer, анимации собраны композицией
**Решение:** бой (`Run`) отдаёт журнал `GameEvent[]`, а показывает его `presentation/animations/GameEventPlayer`: по событию — анимация, звук, всплывающая подпись, обновление HUD. Низкоуровневые анимации — маленькие компоненты, собранные композицией в `Animations`:
- Attack — `MeleeAttack` (бросок рукой), `RangedAttack` (`shot` стрела / `bolt` молния), `BackstabAttack` (удар в спину); общий интерфейс `IAttackAnimation`, выбор в `AttackAnimations.pick()` по стилю события;
- combat — `HitAnimation`, `SpawnAnimation`, `DeathAnimation`, `MoveAnimation`;
- effects — `BurstAnimation`, `ProjectileAnimation`, `FlashAnimation`, `BumpAnimation`, `LootPopAnimation`, `VfxAnimation` (эффекты способностей через `Vfx`);
- text — `FloatingText`; `BackgroundMotion` — «возврат после удара доигрывает в фоне».
Поле: `presentation/board/BoardView` (какая карточка на какой клетке, подсветки) и `BoardLayout` (геометрия клеток). Твины и паузы — через `presentation/phaser/PhaserTweens` и `PhaserClock`.
**Контекст:** `GameScene` смешивала событие, решение об анимации, твины Phaser, VFX, звук и визуальное состояние в одном `switch` на 26 веток.
**Альтернативы:** иерархия `Animations → MageAnimations → FireMageAnimations` — отвергнута: стиль удара приходит в самом событии (его выставляет правило боя по стратегии атаки линейки), других различий анимаций по классам нет, а наследование дублировало бы код между линейками. Папка `animations/classes/` из плана не заведена по той же причине.
**Последствия:** сцена не заводит твинов для событий боя. Новое событие = метод в `GameEventPlayer` (+ компонент в `animations/`, если нужен новый приём). Проигрыватель только читает бой (`IRunState`); всё, что меняет профиль (счётчики сундуков и поломок), учитывается не в нём.

## [2026-09-24] Ввод игрока — команды, бой вызывается только через GameCommandHandler
**Решение:** ввод превращается в `PlayerCommand` (`application/game/interfaces/PlayerCommand.ts`): `select-cell`, `use-perk`, `use-item`, `escape`. Касания поля, стрелки/WASD, 1–3 и Esc переводит `presentation/phaser/PhaserInput`, кнопки HUD шлют те же команды. Боевые команды (`BattleCommand` — всё, кроме `escape`) выполняет `application/game/GameCommandHandler`: он только выбирает метод `IRunSession` (`tap`/`usePerk`/`useItem`) и правил не знает. `escape` — не ход в комнате, а решение потока забега, его обрабатывает контроллер.
**Контекст:** сцена сама решала, что значит касание, и вызывала `run.tap`/`run.usePerk`/`run.useItem` из обработчиков кнопок и клавиш.
**Последствия:** кнопка или клавиша никогда не вызывает `run.*` напрямую; ввод не толкует касание (удар, шаг, подбор или наведение — решает `Run`). Новое действие игрока = новый вариант `PlayerCommand` + ветка в обработчике.

## [2026-09-24] HUD боя — отдельные компоненты по реальным обязанностям
**Решение:** панели вокруг поля — `presentation/hud/`: `Hud` (фасад, реализует `IBattleHud` для проигрывателя событий) собирает `ConsumableBar` (расходники и переключатели «АВТО»), `LootBar` (кошель забега), `RoomInfo` (комната и её свойство), `EnemyCounter`, `ResourceBar`, `StatsRow`, `GearBar` (прочность снаряжения), `PerkBar` (кнопки способностей), `TutorialHint` (подсказка и «палец»). HUD только читает бой (`IRunState`) и обновляется после хода (`Hud.update()`); кнопки отдают `PlayerCommand` через `IHudActions`, а не зовут `run.*`.
**Контекст:** построение и обновление панелей занимало половину `GameScene`; кнопки способностей и расходников напрямую вызывали бой.
**Альтернативы:** набор файлов строго по списку плана — отвергнут: в плане нет прочности снаряжения и ряда характеристик, а они — реальные отдельные обязанности; «Сбежать» и звук — одиночные кнопки, им хватает места в `Hud`.
**Последствия:** константы раскладки живут статическими полями своих компонентов (`ResourceBar.Y`, `TutorialHint.Y`, `ConsumableBar.Y`). Новая панель = новый компонент в `hud/`, подключённый в `Hud`. Подсветку целей заряженной способности рисует поле (`BoardView.showTargets`), а не HUD.

## [2026-09-24] Phaser — деталь реализации: поток боя говорит с отрисовкой через интерфейсы
**Решение:** `application/game/interfaces/` описывает, что потоку боя нужно от внешнего мира: `IClock` (паузы, общий порт в `application/ports`), `IInput` (команды игрока), `IAnimationPlayer` (проиграть события), `IGameRenderer` (показать состояние после хода, отказ, заряд способности, подсказки обучения), `IGameDialogs` (решения игрока в окнах — промисами), `IGameNavigator` (уход в следующую комнату, новый забег, хаб). Реализации на Phaser — в presentation: `phaser/PhaserClock`, `phaser/PhaserInput`, `phaser/PhaserRenderer`, `animations/GameEventPlayer`, `dialogs/GameDialogs`, `navigation/GameNavigator`; твины — `phaser/PhaserTweens`.
**Контекст:** поток боя (ход, конец комнаты, гибель, итог забега) был вперемешку с `this.add`, `this.tweens`, `this.time`, `new Dialog(...)` и колбэками кнопок.
**Альтернативы:** общий `PhaserService` с `addImage/addText/addTween/delay/camera` — запрещён планом: он переносит God Object из сцены в сервис. Окна с колбэками вместо промисов — отвергнуты: ветка «гибель → видео не досмотрено → окно снова» превращалась в рекурсию колбэков.
**Последствия:** код потока боя не импортирует `phaser` и не трогает объекты сцены. Модальное окно отвечает промисом выбора игрока. Новое, что поток должен показать, — новый метод в порте и его реализация в presentation, а не вызов Phaser из потока.

## [2026-09-24] GameScene — координатор; поток боя в GameController, учёт забега в TowerRun, правила профиля в Profile
**Решение:**
- `presentation/scenes/GameScene` (≈80 строк) — цикл Phaser, сборка вида боя и связка с контроллером; ни правил, ни команд, ни анимаций, ни учёта.
- `application/game/GameController` — поток комнаты: команда → ход → итог хода (победа, гибель, «Возвращение», автоприменение, обучение) → конец комнаты → гибель и воскрешение за видео → итог забега. С игроком говорит через порты этапа 4, с платформой — через `IPlatform` (`application/ports`), с рекламой — через `AdService`.
- `application/game/TowerRun` — учёт забега в профиле: вход в комнату (`Run` собирает `RunFactory`), счётчики сундуков и поломок, износ и расходники, оплата пройденной комнаты, рекорд, таблица рекордов, автопрокачка, удвоение награды.
- `application/ads/AdService` — политика рекламы: rewarded только по желанию игрока, interstitial — в паузах, не раньше `AD_POLICY.firstAdAfterRooms` комнат и не чаще собственного кулдауна.
- `domain/logic/profile/Profile` — правила над документом сохранения, вынесенные из `Store` (кошельки героев, лавка, награда дня и «Дар башни», рекорды, счётчики, достижения, настройки автоматизации); время приходит снаружи (`now`), события — доменные `Signal` вместо `Phaser.Events`.
- `infrastructure/store/Store` — только загрузка (локально + облако, побеждает свежее), перенос старых форматов, отложенная запись; реализует порт `IProfileStorage`.
**Контекст:** в `GameScene` вперемешку были поток боя, учёт в профиле через `Store`, вызовы SDK и рекламы; правила кошелька, лавки, наград и достижений лежали в инфраструктурном `Store` рядом с `localStorage` и `Phaser.Events`.
**Альтернативы:** порт `IProfileService`, который реализует сам `Store`, — отвергнут: правила остались бы в инфраструктуре, и проверить их без браузера было бы нельзя.
**Последствия:** application зависит от `Profile` (домен), а не от `Store`. Правило про золото, награды или достижения пишется в `Profile`, а не в сцене и не в хранилище. Экраны второго цикла до своей миграции обращаются к `Store.profile` — это переходное состояние, его снимают этапы 9–15. «Пропадёт ли добыча комнаты» считается по бою (`run.totals`), а не по отображению кошеля. `GameScene.controller` открыт только для отладки и проверок.

## [2026-09-24] Метаморфозы: определение класса отдельно от героя, класс выводится из прогресса
**Решение:**
- `ClassDefinition` (`domain/data/classes/interfaces`) — что класс даёт любому герою: линейка, ступень, родитель, база (база линейки + бонусы класса), способности по слотам, таланты, куда ведёт метаморфоза. Собирается шаблонным методом `HeroFactory.createClassDefinitions()` из продуктов той же фабрики; реестр — `CLASS_DEFINITIONS`.
- `Hero` (`domain/logic/hero`) — один экземпляр на открытую линейку (его держит `Profile`): прогресс дерева, текущий класс, `canMetamorphose()/metamorphose()`, `cancelMetamorphosis()`, `combatStats()`. Текущий класс — самый развитый открытый класс линейки: он выводится из прогресса и отдельно не хранится.
- `Profile.activeClass` выводится из `activeHero`; сохранённый `activeClass` лишь выбирает активного героя (линейку). Документ кошелька героя в профиле называется `heroSave`/`heroSaveOf()` — чтобы не путать с сущностью `Hero`.
**Контекст:** «герой» был размазан по `Store` (`activeClass`, `lineages`, `heroes`, `weapon`) и функциям `skillTree`/`stats`; класс хранился дважды — в `activeClass` и в дереве, — и dev-параметр мог их развести.
**Альтернативы:** хранить класс в поле героя и менять его при метаморфозе (`hero.classId = 'pyromancer'`) — отвергнуто: поле может разойтись с деревом, план прямо запрещает такой переход. Перенести в `Hero` и кошелёк — отложено: у операций с кошельком побочные эффекты уровня профиля (счётчики заработанного, достижения, сигнал кошелька).
**Последствия:** метаморфоза и её отмена — только через `Hero` (проверяет ступень, ворота яруса и занятую соседнюю ветку); души списывает вызывающий. Формат сохранения не менялся. Dev-параметр `?class=` открывает продвинутый класс всей цепочкой метаморфоз. Проверки — раздел «определения классов и герой» в `npm run selftest`.

## [2026-09-24] Класс героя — состояние, стиль боя линейки — стратегия, различия в числах — данные
**Решение:**
- `HeroClassState` (`domain/logic/hero/hero-class-state`) — состояние «герой играет за класс» (State): id, линейка, ступень, родитель, стиль атаки, `getStats()`, `getAbilities()`, `next`, `canBecome()`. Один класс на все классы игры, экземпляр — по одному на класс (`HeroClassState.of(id)`, приспособленец), собирается из `ClassDefinition`. `Hero.classState` выводит состояние из прогресса дерева; метаморфоза переводит того же героя в состояние другого класса.
- Стиль боя линейки — стратегия `IAttackStrategy` (`domain/logic/hero/attack`): бьёт ли рукой (`melee`), базовое действие (`mode`), досягаемость `reaches(from, to, passives)`, множитель (`mul`), гарантированный крит, стиль анимации. Реализации: `HandAttack` (воин), `SpellAttack` (маг), `ShotAttack` (лучник, вместе с «Косым прицелом» и «Орлиным глазом»), `BackstabAttack` (наёмник). Стратегию выбирает фабрика линейки (`LineageDef.attack`), бой читает её из `PlayerStats.attack`.
- Цена спасения от смерти — данные линейки `LineageDef.cheatDeathPrice` (`drainsResource`, `goldShare`): маг сжигает ману, наёмник отдаёт 20% золота комнаты.
- Удалены таблица `BASIC` и тип `BasicMode` из `stats.ts`, поля `melee/ranged/rangedMul/rangedCrit` из `PlayerStats`, `LineageDef.melee`, `Run.archerReach()` и ветки `lineage === 'mage' | 'mercenary'` в `Run.tryCheatDeath()`. `Run.backstabs` стал приватным.
- Анимации атак в presentation переименованы: `MeleeAttackAnimation`, `RangedAttackAnimation`, `BackstabAnimation` — чтобы не путать с доменными стратегиями (запись «Анимации боя…» выше называет их старыми именами).

- Шаги переноса `SAVE_MIGRATIONS` (порт `SaveMigration`: `id`, `applies`, `migrate`) над документом прошлых версий `LegacySave`: `PerItemAutoUse` (общий переключатель автоприменения → по расходнику, значения по умолчанию, приведение к `true/false`) и `SharedWalletToHeroes` (общий кошелёк, расходники, доспех и пройденные комнаты → кошельки и рекорды героев; старые поля убираются). Новый шаг добавляется в конец списка.
- `ProfileStore` читает локальное и облачное сохранение, отдаёт их `SaveFormat` и записывает изменения; своего `merge` и версии у него больше нет, из переходного списка сложности ESLint он убран.
- Новая цепочка сверена со старым `merge` (взят из git) на семи документах разных лет — текущий, общий кошелёк списком комнат, комнаты по линейкам, выключенный общий переключатель, автоматизация без переключателя, частичные группы с лишним старым полем, `heroes: null` — результаты совпали полностью. selftest проверяет формат и каждый шаг: текущий документ не меняется, читается только текущая версия, побеждает более свежее, общий кошелёк уходит активной линейке, открытые линейки получают пустые кошельки, комнаты по линейкам дают рекорды, старые поля убраны, автоматизация, недостающие поля.
**Контекст:** этап G3 второго круга. Перенос старых форматов жил приватным методом инфраструктуры на 50 строк и не проверялся ничем; добавить новый шаг можно было только правкой этого метода.
**Альтернативы:**
- Номер версии на каждый шаг (`v: 3`, `v: 4`) — не стали сейчас: прошлые изменения формата версию не поднимали, и шаги узнают свой документ по форме; следующий шаг может проверять `v`, а `accepts` — принимать диапазон версий.
- Шаги как чистые функции `(doc) => doc` — не стали: у шага есть имя и условие, по которым selftest проверяет, что текущий документ не трогается.
**Последствия:** изменение формата сохранения — новый шаг в `SAVE_MIGRATIONS` с проверкой в selftest, поля по умолчанию — в `freshSave`. Инфраструктура сохранений о правилах формата не знает. Формат и поведение не менялись; selftest и sim совпадают побайтно.
