# GOTCHAS

Неочевидные особенности проекта. Не баги (или баги, которые не будем чинить) —
просто вещи, которые надо знать, чтобы не наступить второй раз.

## Поля сцены не должны совпадать со свойствами Phaser.Scene
`Phaser.Scene` уже содержит `anims`, `renderer`, `sound`, `time`, `tweens`, `events`,
`data`, `input`, `add`, `make`, `cameras`, `scale`, `registry`, `plugins`, `children`,
`physics`, `lights`, `game`, `sys`. Приватное поле с таким именем в подклассе сцены
ломает компиляцию («Property … is private in type … but not in type 'Scene'»), а без
TypeScript молча подменило бы сервис Phaser. Поэтому в `GameScene` проигрыватель
анимаций называется `animations`, а отрисовка — `view`.

## Экземпляр сцены живёт дольше одного запуска
Phaser создаёт сцену один раз и при каждом `scene.start()` снова вызывает
`init()` и `create()` на том же объекте. Всё состояние запуска (флаги, ссылки на
кнопки, контроллер) обнуляется в `init()`, иначе оно переживает выход из сцены.

## «Run» в имени — это забег, бой в комнате — `RoomBattle`
Бой в **одной комнате** (поле, ход, способности, ответ врагов) — `RoomBattle`
(`domain/combat/room-battle`), переменная — `battle`. Слово «run» в именах кода значит
**забег** — цепочку комнат с 1-1 до гибели или ухода: `TowerRun` (`application/game`), его
состояние между комнатами — `RunCarry` (здоровье, ресурс, пройденные комнаты, заработанное),
итог — `RunSummary`. `BattleCarryStats` — только то, что герой уносит из комнаты в комнату
внутри боя. До второго круга рефакторинга бой назывался `Run` (`RunFactory`, `IRunSession` …)
— под этими именами он встречается в старых записях `PROJECT-DECISIONS.md`.

## Содержимое героя сравнивают по id, а не по ссылке
Линейки, классы, способности и таланты — единственные объекты-определения (`heroes/<линейка>/`),
поэтому реестры держат одни и те же объекты. Но проверки собирают свои определения — сравнивать
содержимое нужно по `id`, а не по ссылке. Стратегии атаки — одни на всю
игру (`ATTACK_STRATEGIES` в `combat/attack`, линейка называет стиль по id `LineageDef.attack`),
их можно сравнивать и по ссылке.

## Способность, перк и механика — три разных id
Способность (`AbilityDef`) адресуется по своему `id` (`lightning`): тексты `ability.<id>.*`, значок
`ability_<id>`, перезарядки и «раз за комнату» в бою, команда `use-perk` и события `perk`/`armed`.
Перк — место способности в дереве, его id — `<класс>_<слот>` (`mage_start`), по нему живут только
узлы дерева и `PERK_BY_ID`. Механика (`AbilityDef.behavior`) — что умеет бой: по ней реестр
`ABILITY_BEHAVIORS`, пассивки (`PlayerStats.passives`) и числа пассивок (`RoomState.paramsOf`).
Сейчас у каждой способности id совпадает с механикой, но проверять пассивку по id способности или
способность по id перка — ошибка: после переноса или второй способности на той же механике она
молча перестанет работать. «Перк» в именах методов боя и HUD (`usePerk`, `perkReady`, `PerkBar`) —
кнопка способности на поле, принимают они `AbilityDef` или id способности.

## Сохранение помнит место таланта, а не талант
У таланта два id: по смыслу (`TalentDef.id`, `thick_skin` — название в словарях) и место в дереве
(`TalentPlace.id`, `warrior/g1-1` — выводится из позиции: класс, путь, ярус, шаг). Ранги в
сохранении (`LineageSave.ranks`, узлы `tal/<место>`) записаны по месту. Переставили таланты в
`talents/<класс>.ts` — у старых сохранений ранги останутся на прежних местах и достанутся тому,
кто теперь там стоит. Хранить ранги по id таланта — изменение формата сохранения (шаг в
`SAVE_MIGRATIONS`).

## Маски Phaser не влияют на ввод
Маска прячет объект только на экране: поиск объекта под указателем в Phaser её не учитывает.
Кнопка, уехавшая за край маскированного списка, остаётся кликабельной и при `topOnly`
перехватывает нажатия у того, что под ней (так появился BUG-001 — мёртвый крестик лавки).
`ScrollList` поэтому отбрасывает попадания в своё содержимое, когда указатель вне списка:
свой список с маской делать через `ScrollList`, а не маской поверх контейнера.

## Общие компоненты интерфейса не знают об инфраструктуре
Компоненты `presentation/components` получают данные через узкие интерфейсы (`IWalletSource`,
`IHeroCardSource`, `IMuteSwitch`), которым `Profile` и `AudioSettings` соответствуют сами, а звук
отклика — через `UiSound`, который подключает корень композиции (`GameCompositionRoot`). Импорт
реализаций портов (`ProfileStore`, `WebAudioPlayer`, `YandexPlatform`) в presentation — ошибка слоя:
сцена получает службы в конструкторе (`SceneServices`), компонент — через интерфейс.
